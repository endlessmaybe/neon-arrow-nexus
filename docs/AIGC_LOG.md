# AIGC 使用与迭代记录

## 1. 使用工具

- AIGC：ChatGPT（GPT-5.6 Sol，高推理模式）
- 开发环境：Windows + Node.js 24
- 实现：原生 HTML / CSS / JavaScript + Canvas 2D
- 验证：Node.js 自动测试 + Playwright Chromium 实际浏览器验收

## 2. 原始需求

本次人机协作从下面这条真实要求开始：

> 完成课程页面中的“一箭又一箭”个人作业，做到正式提交之前；游戏要比作业基础要求更有新意，并且画面要炫彩。

课程公开列表可以确认作业题目是“利用 AIGC 完成‘一箭又一箭’小游戏”。作业正文当前访问会跳转博客园登录页，因此开发过程中没有伪造无法读取的课堂专属评分条目，而是优先覆盖核心玩法、创新、AIGC 记录、源码、测试、README 和博客草稿等常见交付要求。

## 3. 第一次迭代：先解决“随机局面可能无解”

### 问题

如果直接随机生成很多箭，很容易产生互相阻挡的死局。一个小游戏即使画面漂亮，只要偶尔生成无解关卡，演示时就存在明显风险。

### AIGC 给出的设计方向

不从“完整棋盘”向前随机，而是从空棋盘**反向构造**：先放最后应该离场的箭，再放倒数第二个，以此类推。每放一个新箭时，检查它面对当前已存在箭路时能否离场。最后反转构造顺序，即得到一条保证可行的解序。

### 落地

- 9 × 12 网格；
- 箭路长度 1–4 个格点，可以出现折线；
- 固定随机种子保证相同关卡可复现；
- 自动保存生成时的解序；
- 测试程序重新执行整条解序，验证关卡真的可解。

### 验证

`npm test` 实际通过 3 关的确定性和完整可解性测试。

## 4. 第二次迭代：不能只是“原游戏 + 炫彩皮肤”

### 目标

用户明确要求“比作业里面要求的有新意”，因此创新必须影响决策，而不是只改背景色。

### 方案

1. **折光门**：箭的飞行射线进入门后旋转 90°，玩家必须判断完整折线路径；
2. **棱镜箭**：特殊箭提供额外分数和量子能量，改变最优消除顺序；
3. **量子超载**：能量充满后，可主动让一条受阻箭相位穿透一次；
4. **连击系统**：正确连点提高得分，错误点击会中断连击；
5. **三关递进**：从无折光门到双门、再到三门高密度箭阵。

这样创新机制直接改变了玩家对“先点哪一个”的判断。

## 5. 第三次迭代：视觉方向

### 初始设计关键词

`arcade puzzle / neon / cyberpunk / vibrant / dark HUD`

### 最终视觉约束

- 深色宇宙背景，避免大面积亮底影响霓虹效果；
- 青色、洋红、紫色作为主要发光色，金色专门用于奖励/棱镜；
- HUD 使用半透明玻璃层，但信息层级保持高对比；
- Canvas 中使用阴影模糊、粒子、扫描线、星点与动态折光门；
- 交互图标全部使用 SVG，不使用 Emoji 作为系统图标；
- 手机端改为单列布局，按钮保持可触控尺寸；
- 支持 `prefers-reduced-motion`，减少对动画敏感用户的不适。

## 6. 第四次迭代：真实浏览器找问题

静态语法检查通过以后，没有直接认为“完成”，而是启动本地服务让 Chromium 真正运行。

### 发现的问题

浏览器控制台出现 `favicon.ico 404`。这不影响游戏，但会让演示时的控制台不干净。

### 修复

增加 `favicon.svg` 并在页面显式声明站点图标。

### 修复后验证

重新开启全新浏览器会话，控制台为：

```text
0 errors, 0 warnings
```

## 7. 真实交互测试记录

### 碰撞

进入第一关后，通过测试接口找到一条真实受阻箭并执行同一套游戏点击逻辑：

```text
before: lives = 4
after : lives = 3
```

说明碰撞、扣血和连击中断分支实际执行。

### 第一关完整通关

按生成器保存的可解顺序逐条消除：

```text
remaining = 0
best combo = ×20
result overlay = visible
```

### 量子超载

第二关先连续正确清除 6 条箭：

```text
charge = 100%
lives = 4
remaining = 20
```

真实点击“启动超载”，再选择一条原本受阻箭：

```text
charge = 0%
lives = 4
remaining = 19
```

说明受阻箭被能力清除，并且没有错误扣血。

## 8. AIGC 在本项目中的作用与我的判断

AIGC 最有价值的地方不是一次生成大段代码，而是快速提出候选方案、把玩法规则形式化、生成测试思路，再通过真实运行把不可靠部分筛掉。

本项目中特别重要的人工判断包括：

- 拒绝“完全随机”的关卡生成方式，改成可证明可解的反向构造；
- 要求创新机制必须改变策略，而不是只有视觉变化；
- 对 AIGC 输出继续做 Node.js 与浏览器双重验证；
- 不把访问不到的课程评分细则编造成“老师要求”；
- 不让 AIGC 自动完成最后的个人账号发布/提交动作。

## 9. 使用 AIGC 的体会

AIGC 能显著缩短从想法到可运行原型的时间，但“代码生成成功”不等于“软件完成”。真正影响作业质量的是能否把需求转换成可验证约束，再把每一个重要分支实际跑一遍。本项目最终把“关卡是否有解”“错误点击是否扣血”“能力是否真的穿透”“页面是否有控制台错误”等都变成了可以重复检查的结果，这比只展示生成代码更有说服力。
