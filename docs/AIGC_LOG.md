# AIGC 使用记录

## 1. 使用环境

- AIGC：ChatGPT（GPT-5.6 Sol，高推理模式）
- 操作系统：Windows 10
- 正式实现：Python 3.13.1 + pygame-ce 2.5.8
- 测试：pytest + Pygame 虚拟显示冒烟测试
- 打包：PyInstaller 6.22.3，单文件 Windows EXE

### 作业提交版 AIGC 协作摘要

| 阶段 | 我向 AIGC 提出的核心问题 | AIGC 给出的方向 | 我最终怎么处理 |
| --- | --- | --- | --- |
| 需求拆解 | 怎样把“一箭又一箭”拆成可实现、可测试的模块 | 拆成规则层、随机生成、界面、测试和交付材料 | 后续持续用作业原文校正，明确 Python、基础玩法和三档难度不能被扩展功能覆盖 |
| 随机关卡 | 怎样避免随机摆放产生死局 | 反向构造并保留完整解序 | 落地到生成器，再用多随机种子和完整解序回放验证 |
| 技术路线 | 早期网页原型如何转成正式作业 | 迁移核心规则到 Python/Pygame | 最终删除旧 HTML/JS/Node 提交链，只保留 Python 主线 |
| 玩法修正 | 进阶长箭已经完整，但基础单格规则缺失 | 拆分基础/进阶两套生成入口 | 新增 `create_basic_level()`，并补启动选择与存档不能绕过选择的回归测试 |
| UI/交互 | 功能多以后如何避免图标难懂、界面过度装饰 | 统一矢量图标、快捷键和悬停说明 | 实机复查后继续做减法，并加入游戏中 `D` 切换难度 |
| 性能 | 1600×1000 下重复渲染开销较高 | 缓存静态背景/文字/网格，复用全屏 Surface | 保留画质，重新跑基准与全量回归后才保留优化 |
| 测试与交付 | 怎样证明不是“源码看起来能跑” | pytest + headless check + EXE 验收 | 源码、Pygame 逻辑、随机地图和打包 EXE 分层验证，问题回到源码修复后再打包 |

博客正文只放这张压缩后的协作表，下面章节保留完整迭代过程，便于老师查看每次接受、否决和修改 AIGC 建议的原因。

## 2. 最开始的目标

我一开始给 AIGC 的要求比较简单：完成“一箭又一箭”小游戏，但不能只照着基础版本复刻，希望玩法有一点自己的东西，画面也要更完整。

后来把需求逐步收紧成三个不能偏离的条件：

1. 整局一共只有三关；
2. 三关分别是简单、中等、终极困难，而且每次新 RUN 随机生成；
3. 创新必须建立在作业基础玩法已经完成的前提上，不能为了创新把题目本身改没了。

## 3. 第一轮：随机地图先解决“能不能通”

最开始最容易想到的是随机摆箭，但实际推演后发现这种方法很容易出死局。于是和 AIGC 讨论后改成“反向构造”：

- 从空棋盘开始；
- 每次只加入当前一定能离场的候选箭；
- 保存加入顺序；
- 最后把顺序反过来作为完整解序；
- 测试重新按这条解序跑完整关卡。

最后这个思路变成了 `neon_arrow/engine.py` 里的正式生成器。随机性仍然保留，但不会靠运气决定一张图是否有解。

## 4. 第二轮：创新不能只换颜色

在基础玩法稳定以后，继续和 AIGC 讨论“怎样让三关真的有区别”。最后保留下来的机制有：

- 90° 折光门；
- 180° 反相门；
- 成对跃迁环；
- 棱镜充能；
- 量子超载；
- 连击计分。

这里我给自己的限制是：每个机制至少要影响一次玩家判断。比如折光门、反相门和跃迁环直接改变射线路径；棱镜和连击会改变“同样都能点时先点谁更划算”；量子超载提供一次有限的主动破局机会。

中间也走过弯路。有一版为了增加内容做到了五关，后来重新检查题目要求后又收回到三关。现在代码层直接拒绝第 4 关索引，不再只是靠界面文案说“三关”。

## 5. 第三轮：先做过网页原型，但后来发现方向不对

早期为了快速验证规则和画面，曾经使用 HTML / CSS / JavaScript + Canvas 做过一个网页原型。那个版本已经能运行，也做了不少视觉细节。

但后面重新核对作业要求时发现，正式实现应该用 Python。这个问题不能靠“网页也能玩”来糊过去，所以没有继续把网页原型包装成最终成品，而是把规则重新移植为 Python，并使用 Pygame 重写桌面游戏。

后续整理最终提交目录时，网页原型源码、Node 构建脚本和旧 JS 测试已经删除，不再和 Python 主线混放。正式交付以这些文件为准：

```text
main.py
neon_arrow/engine.py
neon_arrow/app.py
dist/NeonArrowNexus-Python.exe
```

这次偏差也让我意识到，AIGC 辅助开发时除了检查“代码对不对”，还要不断检查“方向是不是仍然符合题目”。

## 6. 第四轮：把视觉重新做进 Pygame

Python 版没有简单地做成几个矩形和文字，而是重新在 Pygame 中实现：

- 深色渐变宇宙背景；
- 动态星点、扫描线；
- 多层透明光晕箭体；
- 箭头白色高光；
- 折光门旋转动画；
- 金色反相门；
- 双环脉冲跃迁门；
- 清除/碰撞粒子；
- 关卡、生命、倒计时、积分、连击和能量 HUD。

同时保留窗口缩放，让棋盘位置和格子尺寸随窗口大小重新计算。

## 7. 第五轮：把“看起来能跑”改成“实际测过”

正式 Python 版完成后，补了三层测试：规则层、Pygame 交互层和高级功能层。

### 规则测试

`tests/test_python_engine.py` 检查：

- 关卡数量严格为 3；
- 多组 RUN 下三关箭数都落在各自区间；
- 每一关保存的完整解序都能从头执行到尾；
- 同一 RUN 可以复现；
- 不同 RUN 会生成不同布局；
- 初始局面同时存在安全箭和受阻箭；
- 折光、反相、跃迁真实改变射线路径。
- 第三关的双跃迁与动态相位锁真实进入射线计算；
- 进阶模式三档难度均使用 2–4 格真实长箭体，显示范围与碰撞范围一致；基础模式另外检查为单格逻辑箭。

### Pygame 交互测试

`tests/test_python_app.py` 不只测试纯函数，还创建真实 Pygame Surface，执行界面渲染，然后找到一条安全箭调用正式点击逻辑，确认箭路真的减少、积分真的增加。

### 高级功能测试

`tests/test_python_features.py` 继续检查：

- `U` 撤销能够恢复一次真实游戏操作；
- 自动存档可以写入并重新恢复；
- `A` AI 自动求解会按经过验证的解序清空当前关；
- 每次启动都先进入模式与难度选择；未同时选中两项时不能进入游戏；
- 基础模式实际生成单格四方向箭，进阶模式仍生成多格随机长箭与机关；
- 存档恢复不会绕过启动选择，只有模式和难度匹配时才能继续原进度。

实际结果：

```text
完整测试数量以 docs/TEST_REPORT.md 的最终实测记录为准
```

中间确实做过“第三关唯一解”和单格内视觉长箭的实验，但试玩后发现它反而会让答案链过于机械，而且显示的箭长与真实碰撞范围脱节，所以最终版本主动撤销了这条路线。现在**进阶模式**三档难度统一使用 13×16 棋盘上的 2–4 格真实占格箭体，第三档为 38–42 条，并通过双跃迁、折光/反相、动态相位锁、2 点稳定度和更紧倒计时提高难度。完整解序只用于证明随机地图可通关，不要求玩家只有一种正确顺序。基础模式则保持单格四方向直线判阻，不复用这些进阶机制。

另外继续保留 pytest 内的 64 个 RUN × 3 关压力抽样；最终版本的同类产品视觉对照与保留差异单独整理在 `docs/MARKET_COMPARISON.md`。

另外运行：

```text
python main.py --headless-check
```

本轮实际检查中，第一关安全箭点击后剩余箭路减少、程序保持 `playing` 状态并得到积分，说明它走的是正式游戏逻辑。

## 8. 第六轮：清掉迁移遗留并扩大随机回归

Python 版稳定后，又对仓库做了一次提交前清理。之前为了迁移方便，同时留着 HTML/CSS/JavaScript、Node 构建脚本、旧 JS 测试和 Python 实现，这对开发过程有帮助，但对最终作业反而会造成入口不明确、技术栈看起来不统一的问题。

所以最终版本删除了旧网页实现链，只保留 Python/Pygame 的运行、测试和构建路径，同时增加 `requirements-dev.txt`，把 pytest 和 PyInstaller 的开发依赖也写清楚。

这一轮还继续扩大随机生成测试。这个过程也暴露出另一个问题：高难度不能只看“箭多不多”。唯一解结构曾经作为实验方案出现，但最终没有保留；最后改为由高密度真实长箭、动态路径机制和更紧容错共同制造难度。

## 9. 第七轮：EXE 也单独验收

为了让游戏不依赖用户本机先配 Python 环境，使用 PyInstaller 打成单文件：

```text
dist/NeonArrowNexus-Python.exe
```

打包完成后又直接运行 EXE 的无界面自检，退出码为 `0`；随后让 EXE 自己渲染第三关截图，也正常生成图片并退出。

这一步主要是避免出现“源码能跑，但发给别人后的 EXE 打不开”这种情况。

## 10. 哪些地方没有直接接受 AIGC 的第一版建议

- 没有采用完全随机摆箭，而是改成能验证完整解序的生成方式；
- 没有为了丰富内容保留五关版本，而是回到题目要求的三关；
- 没有因为网页原型已经完成就继续把错误技术方向当最终交付；
- 没有把创新只做成视觉特效，而是要求机制真正进入射线和计分逻辑；
- 没有只检查源码是否能 import，还继续测试 Pygame 和打包后的 EXE；
- 没有因为固定样例都通过就停止测试，而是扩大随机种子覆盖并修复偶发生成失败；
- 没有把“第三关箭更多”直接等同于终极困难；唯一解方案试玩后也撤销，最终改成更高密度、动态机制和更紧容错共同制造难度；
- 没有把迁移阶段的两套技术栈一起塞进最终仓库，而是清理成单一 Python 主线；
- 没有替自己编造姓名、学号、仓库地址等个人提交信息。

## 11. 使用体会

这次最明显的感受是，AIGC 很适合快速把一个想法推进到可以讨论、可以运行的状态，但它并不会自动保证“当前方向一定符合题目”。网页原型就是一个很典型的例子：做得再完整，语言不符合要求也不能算完成。

所以后面我的使用方式逐渐变成：先让 AIGC 帮忙发散和实现，再把题目约束、关键规则和易出错分支写成可以重复执行的检查。这样即使后面继续改 UI 或玩法，也比较容易知道有没有把原本正确的东西改坏。

## 12. 最终调整：撤销唯一解，恢复真实随机长箭

最后一次试玩后又撤销了第三关的唯一解约束。原因不是生成器做不到唯一解，而是为了维持 42–48 条高密度唯一链，箭身被压缩成了单格内的小折线，玩法反而偏离了最初“随机长箭互相阻挡”的直观感觉。

最终版本把**进阶模式三档难度**统一回同一套反向构造生成器：每根箭真实占用 2–4 个格子，箭身可直行或在尾部随机 90° 转折，末段始终与箭头方向一致；不同箭体不能共格，也不能占用机制格。随后又把终极困难扩展到 13×16 棋盘和 38–42 条箭，并加入第二组跃迁环、第五座折光/反相门以及三道动态相位锁。相位锁分别在剩余箭数降到 30 / 20 / 11 条时解除，生成器会重新按当前阶段验证完整通关路径，并保证新机制确实参与至少一条开局射线。

最终仍不要求唯一解，玩家可以在多个安全选择之间自己判断路线；难度改由高密度真实长箭、双跃迁、动态相位封锁、2 点稳定度和 120–136 秒倒计时共同形成。并保留 `64 RUN × 3 关` 随机生成压力测试；最终测试数量、EXE 哈希与截图验证统一以 `docs/TEST_REPORT.md` 为准。

## 13. 第八轮：同类产品调研后做“产品化”而不是继续堆机制

2026-09-16 又查了一轮仍在分发的 Arrow Escape / Tap Away 同类产品。市场上除了 Hint / Undo / Combo 以外，还经常出现 route/grid guide、Daily / Zen / Challenge、主题皮肤、离线进度和 reduced motion 等能力。

这次没有把所有功能照单全收。因为课程硬要求仍然是三关，所以 Daily、Endless、Boss、排行榜等会扩张关卡体系的东西没有加入；真正落地的是两项不会破坏题目边界、又能明显提高完成度的能力：

- 悬停交互改为纯视觉高亮，不再自动调用 `trace_arrow()` 泄露安全/危险；随后进一步删除 `H` 安全箭扫描入口，界面不再提供“安全出口/安全箭”提示；
- `V` 低动态模式：跳过启动动效、冻结持续装饰运动、减少粒子数量和速度，同时继续保留文字/颜色状态。低动态和音效开关都会写入自动存档。

视觉也从“多加一点发光”改成了真正做减法的 Sci-Fi HUD/FUI：启动同步序列压缩到约 1.15 秒，背景删除扫描线、光谱丝带、轨道圈和透视网格，面板/棋盘移除角标与多层框线，按钮去掉玻璃分层、内高光和扫描标记，只保留必要状态色。离场反馈最终也不再把整根 L 形箭刚性平移：正常模式约 0.86 秒，前约 42% 由箭头先向出口前进、箭身沿原折线逐段跟随拉直，之后继续沿最终方向出屏并在后段淡出。对应测试除了覆盖悬停不泄题、提示入口不存在、离场队列与淡出变化，还加入了“L 形箭头尾端点位移必须不同”的专项回归，避免后续又退回整体平移。

## 14. 第九轮：补回真正的基础模式，并强制启动时选难度

最后自查时又发现一个更基础的问题：虽然前面一直强调“创新建立在题目要求之上”，但正式版本实际上只保留了随机长箭这条进阶规则，作业原始的“单格箭头 + 四方向直线判阻”没有作为独立模式存在。为了避免继续凭自己的理解猜，我又对照了同一课程、同一作业的近期实现，确认基础模式应该明确保留单格逻辑箭，进阶长箭属于扩展玩法。

这次没有把第一档难度简单改名成“基础”，而是在规则层真正拆成两套生成路径：

- `create_basic_level()`：每支箭逻辑上只占 1 格，不使用折光、反相、跃迁或相位锁；三档难度分别提高单格箭密度；
- `create_level()`：保留原来的 2–4 格真实长箭与进阶机制；
- 两套生成器都保存可执行解序，并继续由同一套射线与测试框架验证；
- 单格箭视觉上只画格内短箭身帮助辨认方向，不把这段视觉线当作多格碰撞实体。

启动流程也重新整理：程序每次打开都先进入 `setup`，必须选择“基础 / 进阶”和“简单 / 中等 / 终极困难”后才能开始。已有存档不会被丢掉，但也不会让程序跳过选择页；只有用户选中的模式和难度与存档匹配时，才显示“继续上次进度”。这样“每次打开先选难度”和“保存游戏进度”不再互相冲突。

同时新增启动选择、基础模式单格约束、基础模式可解性、进阶机制仍然存在等自动化回归，并生成新的启动页与基础模式实机截图。GitHub 和博客园的发布材料也只准备到可审核状态，在本人确认前不做远程上传或发布。
