# 《霓虹箭域》玩法与技术设计

## 1. 设计目标

这个版本没有打算把原规则推翻重做。最终把题目主体和创新玩法拆成 **基础模式 / 进阶模式** 两条明确边界，并主要补三件事：

1. **一眼可玩**：点击箭路即可操作，不增加复杂学习成本；
2. **明显创新**：新增机制必须真正影响路线判断和资源决策；
3. **运行稳定**：每次完整开局都能换一套布局，同时又能通过 RUN 种子把某一局重新生成出来，方便定位问题和测试。

## 2. 核心规则模型

### 2.1 基础模式：作业原始规则

基础模式中的每支箭在逻辑上只占 **1 个格子**，方向只有 `up / right / down / left`。点击后从箭头所在格的前一格开始，沿方向逐格检查到棋盘边界：

- 扫描到边界之前没有遇到其它箭：允许离场；
- 任意位置遇到其它箭：判定受阻，箭不消失并扣除 1 次容错；
- 不使用折光门、反相门、跃迁环、相位锁，也不让视觉短箭身参与多格碰撞。

基础模式同样使用反向构造保证可通关。生成器只接受“面对当前已放置箭阵仍能直接离场”的新箭，因此把构造顺序倒过来就是一条完整合法解。三档难度分别生成 18–22、28–34、40–48 支单格箭，难度只由密度、方向关系和消除顺序增加。

### 2.2 进阶模式：随机长箭与机关

棋盘最终采用 13 × 16 格点。扩容的主要原因是终极困难需要同时容纳 38–42 条真实 2–4 格长箭、两组跃迁环和三道相位锁，又不能让箭体互相共格。

每一条箭由以下数据描述：

```text
id       唯一编号
cells    箭路占据的连续格点
head     箭头所在格点
dir      箭头当前方向
color    渲染颜色
prism    是否为棱镜箭
```

玩家点击箭以后，从 `head` 向 `dir` 逐格追踪射线：

- 越过棋盘边界：路径安全，可以清除；
- 命中其他箭占用的格点：发生碰撞；
- 命中折光门：根据门的类型顺/逆时针旋转 90° 后继续追踪；
- 命中反相门：方向翻转 180° 后继续追踪；
- 命中跃迁环：瞬移到配对出口并保持当前方向；
- 命中仍处于开启阶段的相位锁：路径被阻挡；达到该锁的剩余箭数阈值后，同一路径恢复通行；
- 重复经过同一“格点 + 方向”：判定为折光回路，不允许离场。

## 3. 可解性保证

设最终期望的清除顺序为：

```text
A1, A2, A3, ... , An
```

如果一次性把所有 `A` 随机出来，很难保证最后一定存在合法的消除顺序。

这里改成从后往前构造：

```text
先加入 An
再加入 A(n-1)，要求它面对当前 An 时可以离场
再加入 A(n-2)，要求它面对 A(n-1)、An 时可以离场
...
```

普通关卡可以依据反向构造关系得到至少一条合法解序。第三关加入相位锁后，路径可用性还会随剩余箭数变化，因此最终会再按当前阶段不断调用真实 `safe_arrow_ids()` 推导完整安全路径，而不是机械地把构造顺序倒放。

可以把它理解成：生成地图的时候顺便把一条可行的消除顺序一起做出来。相比地图生成完以后再暴力搜索所有排列，这种方式更容易控制，也更适合这个作业的规模。

三关现在统一使用同一套反向构造器。第三关不再为了“唯一解”引入特殊依赖链，而是通过 38–42 条真实长箭、只有 2 点稳定度、120–136 秒倒计时、5 座折光/反相门、两组跃迁以及三道阶段相位锁共同提升难度。生成器仍然保存一条经过验证的完整解序，但玩家不必按这条顺序唯一操作，当前棋盘可以同时存在多条安全路线。

箭体恢复为真实占格的随机长线条。每根箭占 2–4 个连续格子，生成时从箭头向后构造身体：紧邻箭头的一段必须与 `dir` 同轴，后面的箭身优先继续直行，也允许随机出现 90° 转折。每一个身体格都参与真实碰撞，不能与其它箭体、折光门、跃迁端点或相位锁共占同一格。

显示层不再额外生成单格内的 `visual_route`。`app.py` 直接把 `cells` 对应的格子中心连成粗线，因此玩家看到的长箭体就是规则引擎实际使用的占用范围，鼠标命中同样覆盖这些真实线段。这样视觉与碰撞重新保持一致，也恢复了之前明显的长短随机差异。

测试会检查三关都实际出现 2 / 3 / 4 格箭体、不同箭体不重叠、末段方向与箭头一致，并验证完整解序仍然可以清空关卡。针对第三关还会额外确认两组跃迁、三道相位锁阈值、锁前阻挡/锁后放行，以及每张图至少有一条开局射线真实受相位锁影响。

## 4. 创新机制

三关按课程要求组织，并形成固定难度梯度：

- **第一关 / 简单**：18–22 条箭，纯路径判断，5 点稳定度；
- **第二关 / 中等**：27–32 条箭，引入两座折光门，4 点稳定度；
- **第三关 / 终极困难**：38–42 条随机长箭，2 点稳定度，120–136 秒，叠加 5 座折光/反相门、两组跃迁和三道相位锁，但不要求唯一解。

整局只会按索引 `0 → 1 → 2` 走完三关，越界索引直接拒绝，不会偷偷回到第一关形成“第 4 关”。选择“重新开始（三关）”时会创建新的 `session_seed`，因此会换一套地图；如果只是本关失败后重试，则继续保留原来的 RUN，避免地图突然变化。

### 4.1 折光门

折光门会直接修改射线方向，所以碰撞检测和关卡生成都走同一个 Python `trace_ray()`。这样生成阶段与实际游玩阶段使用的是同一套路径规则，不需要另外维护两份判断逻辑。

### 4.2 棱镜箭

每隔一段生成特殊棱镜箭。成功清除获得额外积分和能量，让“立即能消除的箭”之间也存在价值差异。

### 4.3 量子超载

玩家通过连续正确操作获得能量。能量 100% 时可以激活一次相位穿透，使下一条被阻挡箭直接清除。它的作用是：

- 提供主动能力，避免只有被动试错；
- 给高连击持续操作一个明确奖励；
- 即使玩家打乱标准解序，也有一次纠错/破局机会。

### 4.4 双跃迁与分阶段相位锁

第三关使用 A / B 两组独立跃迁环，使射线可能跨越多个棋盘区域继续传播。P1 / P2 / P3 三道相位锁分别在剩余箭数降到 30 / 20 / 11 条时解除；开启时它们是实际碰撞阻挡，解除后同一格变为可穿过状态。这个设计让同一张随机图在前、中、后期出现不同的路径关系，而不是只靠堆更多箭增加难度。

### 4.5 自主判断与离场动画

悬停只承担命中确认和轻量高亮，不调用 `trace_arrow()`，也不提前显示安全/危险、出口或阻挡点。界面不再提供 `H` 安全箭扫描或其它“安全出口”提示，玩家需要根据箭头方向和棋盘机制自己判断；完整演示仅由独立的 `A` 自动求解功能承担。

成功点击后，箭体不会瞬间从棋盘删除。逻辑层立即把它从碰撞集合中移除，渲染层则保留一份瞬时快照：正常模式约 0.86 秒、低动态模式约 0.60 秒。离场不是把整根 L 形箭作为一个刚体平移，而是把原箭身折线当作连续路径：前约 42% 动画由箭头先进入出口射线，尾部依次沿原折线路径跟随并被拉直；随后整条已拉直箭体继续沿箭头方向出屏，最后阶段再连续淡出。最后一根箭也会先完成这段可见离场，再出现结果面板。这样把“判断正确”和“箭确实离场”连成一个肉眼可辨的连续空间反馈。

### 4.6 低动态模式

新增 `V` 低动态模式。启用后，持续背景运动与机制脉冲改为静止帧，启动动画直接跳过，消除粒子数量和移动速度明显降低；必要的文字、颜色和状态反馈仍保留。低动态与音效状态统一进入设置持久化。

## 5. 状态机

```text
setup
  ├─ 选择基础 / 进阶模式
  ├─ 选择简单 / 中等 / 终极困难
  ├─ 新开所选难度 → playing
  └─ 模式与难度匹配已有存档 → 继续上次状态

ready
  ↓ 开始
playing
  ├─ 第 1/2 关清空 → level_complete → 下一关
  ├─ 第 3 关清空   → campaign_complete → 重新开始（三关）
  ├─ 稳定度归零    → failed
  └─ 时间归零      → failed

failed → 本关重试（保留 RUN）
```

程序每次启动都强制回到 `setup`，不会因为上次有存档就直接跳进游戏。存档本身仍保留；只有玩家主动选中与存档一致的模式和难度时，界面才提供“继续上次进度”。这样同时满足“每次打开先选难度”和“保存游戏进度”两个要求。

第三关结束后状态直接进入 `campaign_complete`，没有任何“继续下一关”的分支，因此不会出现隐藏的第 4 关。

## 6. 渲染与逻辑解耦

`neon_arrow/engine.py` 不依赖 Pygame，只负责：

- RUN 种子与分关种子的混合；
- 随机难度区间生成；
- 箭路生成；
- 占用表；
- 射线追踪；
- 折光门转向；
- 反相门与跃迁环；
- 动态相位锁与阶段阈值；
- 可解性验证。

`neon_arrow/app.py` 负责：

- 每次启动的模式与难度选择，以及与存档匹配后的继续入口；
- 游戏状态；
- Pygame 窗口和绘制；
- 鼠标/键盘输入；
- 得分、生命、计时与能力；
- 三关练习选择与通关星级评价；
- 撤销和 AI 自动求解；
- 自动存档与恢复；
- 程序内动态音效；
- 箭头离场动画与辅助设置持久化；
- 首帧直接呈现完整交互界面，并支持低动态降级；
- 粒子反馈；
- HUD 与结果层。

这样拆开以后，规则部分可以直接用 pytest 测试，不需要为了验证一次射线判断先启动整个游戏窗口；界面层则另外用 SDL 虚拟显示做 Pygame 渲染与点击冒烟测试。

## 7. 视觉系统

### 颜色语义

- 青色：主交互、正常能量；
- 洋红/紫色：量子、折光和高能状态；
- 金色：棱镜、提示与奖励；
- 红粉色：碰撞和危险；
- 深蓝黑：背景和玻璃面板。

颜色之外仍辅以文字、形状、动画和状态变化，不只依赖色彩传递结果。

### 动效原则

- 程序启动优先保证可用性与展示一致性：首帧直接呈现完整 UI，不再用近黑色同步序列覆盖真实界面；
- 箭路成功：箭头先走、箭身沿原折线依次跟随拉直，再沿最终箭头方向完整飞出窗口，并在起点出现短促粒子爆发；
- 碰撞：红色粒子 + 棋盘短促震动；
- 棱镜：更密集的高亮粒子；
- 超载：能量达到 100% 后按钮进入高亮可激活状态；
- 折光门和跃迁环持续做低幅度旋转/脉冲，让机制位置容易识别但不过度干扰判断；
- 相位锁开启时显示红色封锁符号，解除后切换为绿色状态，玩家不需要猜隐藏规则。

### 高级化视觉层级

界面继续使用深蓝黑 + 青/紫/洋红作为主视觉，但主动降低装饰密度：背景只保留渐变、两处低透明色雾和稀疏星点，删除扫描线、光谱丝带、轨道轮廓与透视网格；面板统一为单层暗底 + 1px 弱边线；按钮移除双层明暗面、内高光、角标和移动反射线，只保留状态色边框与轻微按压位移；棋盘也删除坐标标记和多层框线。悬停只强化当前箭体轮廓，不用绿/红状态或文字替玩家判断。

离场动画只改变被点击箭体自身的可见几何，不拉出额外“答案轨迹”。折线箭会像沿自身轨道被依次抽走，而不是整根形状平移；这样既保留正确操作的空间连续性，也避免把视觉反馈变成解题提示。

## 8. 窗口缩放

Python 版是桌面程序，不再用网页断点。Pygame 窗口允许缩放，`board_geometry()` 会根据当前窗口尺寸重新计算侧栏宽度、棋盘容器、格子尺寸和原点位置。程序设置了最小窗口尺寸，避免缩得过小后 HUD 与棋盘互相覆盖。

## 9. 后续如果继续做

现有引擎还可以继续往下面几个方向扩展：

- 每日种子挑战；
- 每日种子排行榜；
- 关卡编辑器；
- 完整操作回放与录像导出；
- 本地最高分与成就；
- 更完整的搜索器，用于估算关卡难度和最少提示次数。
