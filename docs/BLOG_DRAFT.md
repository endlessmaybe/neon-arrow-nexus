## 二、我先处理的不是特效，而是“随机地图会不会死”

最开始看这个游戏时，规则似乎很简单：箭头前面没东西就能点，有东西就不能点。但真正做随机地图后很快就遇到一个问题——如果直接随机摆箭，很容易生成互相堵死的局面。

所以我没有采用“生成一张图，再赌它能不能通”的方式，而是反过来构造关卡。

假设最终正确消除顺序是：

```text
A1 → A2 → A3 → ... → An
```

生成时从 `An` 开始。每加入一条新箭，程序都会用真实的射线规则检查它在当前棋盘上是否能安全离场。等全部放完后，把构造顺序反过来，就得到一条完整的可行解序。

Python 里的关卡生成大致是这样：

```python
while len(construction_order) < config["target"]:
    candidate = _generate_candidate(...)
    if candidate is None:
        continue

    for cell in candidate["cells"]:
        occupied[(cell["x"], cell["y"])] = candidate["id"]

    construction_order.append(candidate)

solution_order = derive_solution_order(level)
```

生成完还不算结束，程序会按当前剩余箭、折光/反相、跃迁以及动态相位锁重新推导一条完整安全路径，测试再复制整关实际执行。如果中间任何一条箭不能离场，这张图就不能通过测试。

## 三、基础模式和进阶模式怎么区分

### 基础模式：先把题目本身做完整

基础模式不使用多格箭身和机关。三档难度分别随机生成 18–22、28–34、40–48 支单格箭，统一保留 3 次容错；难度主要来自箭头密度和消除顺序，而不是额外机制。

视觉上我仍然给单格箭画了一小段短箭身，避免只有一个三角形时方向不够直观，但这段线只是显示效果。碰撞表里每支箭仍然只占自己的一个格子，所以基础模式的判定规则没有被视觉效果偷偷改掉。

### 进阶模式：再在基础规则上做扩展

### 第 1 关：简单

进阶简单档随机生成 18–22 条 2–4 格长箭，稳定度为 5。主要目的是先熟悉真实长箭身的阻挡范围，同时接触连击和棱镜充能。

### 第 2 关：中等

第二关随机 27–32 条箭，加入两座 90° 折光门。

箭的射线经过折光门以后会改变方向，因此不能只看箭头正前方。比如一条看起来马上要飞出边界的箭，经过折光门之后可能转向棋盘内部，再撞到另一条箭。

### 第 3 关：终极困难

第三关进一步提高到 38–42 条箭，稳定度只有 2，倒计时缩短到 120–136 秒。为了容纳更多真实长箭与机制，棋盘扩展到 13×16。除了折光、反相，这一版还加入了双跃迁与分阶段相位锁：

- 90° 折光门；
- 180° 反相门；
- 两组成对跃迁环；
- P1 / P2 / P3 三道相位锁，分别在剩余箭数降到 30 / 20 / 11 条时解除。

反相门会让射线直接掉头，跃迁环会把射线从一个端点瞬移到另一个端点，然后沿当前方向继续飞。相位锁在开启阶段会真实阻挡射线，达到对应剩余箭数后才放行。它们全部走同一套 `trace_ray()` 逻辑，不是只画在棋盘上的装饰。

第三关不再强制唯一解。程序仍然会为每张随机地图构造并验证至少一条完整通关顺序，但玩家可以自己选择路线。生成器会避开贴边直接朝外的明显送分箭，并要求每张第三关至少有一条开局射线确实被相位锁挡住。难点来自 38–42 条真实长箭、只有 2 点稳定度、更紧的时间，以及折光、反相、双跃迁和阶段解锁的叠加，而不是被迫背一条固定答案链。

画面上每根箭现在直接占 **2–4 个真实格子**。它可以是一条直线，也可以在尾部随机出现 90° 转折；连接箭头的最后一段永远与箭头朝向一致。后来我拿 Tap Away / Arrow Escape 一类同类小游戏逐项对照后，发现真实长短交错比“单格里做几个小数长度档位”更自然，所以直接恢复了多格长箭。

这次显示和碰撞重新统一：箭身经过的格子就是它真正占用的格子，生成器会禁止不同箭体共格，也会避开折光门和跃迁端点。整段箭身都可以点击，不会出现“看起来被一条线挡住，规则却当它不存在”的情况。完整同类产品对照记录在 `docs/MARKET_COMPARISON.md`。

## 四、我额外加的玩法

### 1. 棱镜箭

部分箭带棱镜标记。成功消除后除了正常得分，还会给更多量子能量，所以“当前能点的箭”之间也有优先级差异。

### 2. 量子超载

连续正确消除会积累能量，达到 100% 后可以按 `O` 或点击按钮激活量子超载。

超载只对下一条受阻箭生效：这条箭可以进行一次相位穿透，不损失稳定度，然后能量清零。这样它能在困难局面里救一次场，但不会把原本的解谜规则直接废掉。

### 3. 连击计分

连续判断正确时连击会上升，单次得分也会提高；碰撞后连击归零。这样除了通关之外，还可以追求更好的操作顺序和更高分数。

### 4. 提示

最终版本删除了 `H` 安全箭扫描功能。悬停不会告诉玩家哪一条可以直接离场，界面也不会显示“安全出口”式提示；需要完整演示时只能单独启动 `A` 自动求解。

## 五、Python 版的界面

我希望它看起来不像“为了交作业临时画几个方块”，但也不想为了所谓科技感把所有装饰都堆上去，所以最终版把视觉重新做了一次减法：

- 深色渐变背景、两处低透明色雾和稀疏动态星点，删除扫描线、光谱丝带、轨道圈与透视网格；
- 面板、按钮和棋盘统一为单层暗底 + 弱边线，删除角标、玻璃双层高光和按钮扫描标记；
- 多层发光箭体和白色箭头高光；
- 折光门旋转动画；
- 反相门单独使用金色编码；
- 跃迁环使用双环脉冲效果；
- 相位锁会按当前剩余箭数显示红色封锁或绿色解除状态；
- 消除和碰撞都有粒子爆发；
- 左侧 HUD 实时显示剩余箭路、稳定度、倒计时、积分、连击和量子能量。
- 支持 `U` 撤销、`A` AI 自动求解、自动存档/恢复和 `M` 音效开关；
- 每次程序启动都先显示模式与难度选择页；`B / N` 可选基础 / 进阶，`1 / 2 / 3` 选择难度，`Enter` 开始；
- 如果已有存档，只有先选中与存档一致的模式和难度，才会出现“继续上次进度”，避免启动后直接跳进一局不知道是什么难度的游戏；
- 通关后会给出 1–3 星评价，并可返回模式与难度选择页重新开局；
- 成功箭不是整根 L 形一起平移：箭头先向出口走，后面的箭身沿原折线依次跟随拉直，再继续沿最终方向离场，最后阶段淡出。

窗口可以自由缩放，程序会重新计算棋盘格大小和位置。

## 六、这次 AIGC 是怎么参与的

这次没有把“一句话生成整个游戏”直接当成最终结果。我把它更多当成一个一起迭代的开发助手。

前几轮主要讨论玩法、随机生成和视觉方向。早期甚至做过一个 HTML/JavaScript 网页原型，后来重新检查作业要求时发现正式实现应该使用 Python，因此没有继续拿网页版本当最终交付，而是把核心规则重新移植成 Python，并用 Pygame 重写了运行界面。最终整理提交目录时，旧网页源码、Node 构建脚本和旧 JS 测试也全部移除，只保留 Python 主线。

这个过程反而让我更明确地看到：AIGC 生成“能看”的东西很快，但是否符合题目、是否真的使用要求的语言、随机地图是否可解、打包后的成品能不能运行，这些都还需要继续检查。

## 十一、这次作业的一个教训

这次最值得记住的问题其实不只是某个算法，而是两个容易在“看起来已经完成”后被忽略的问题：一是中途出现过技术方向偏差，网页原型已经做得比较完整，但重新核对要求后发现正式实现语言不对；二是为了追求“困难”不断叠加约束，也可能把本来直观的小游戏做得过度复杂。

如果只因为“现在这个已经能跑了”就继续往错误方向堆功能，最后花的时间会更多。所以后面我把“有没有满足题目约束”也当成测试的一部分，而不是只检查程序有没有报错。

最后我把第三关从唯一解约束退回到“随机长箭 + 至少一条完整可解路径”。这样仍然保留随机地图的可解性和 RUN 可复现性，但玩家不必机械寻找唯一一步，玩法更接近最初的“一箭又一箭”。

从技术上看，我觉得这次最有价值的是随机地图的可解性、可复现性，以及视觉和碰撞规则的一致。画面特效很直观，但真正决定这个小游戏能不能稳定随机玩的，是生成器不能给出死局，而且玩家看到的箭身必须和程序实际判定的阻挡范围一致。

## 十二、总结

最后的版本没有再让扩展玩法覆盖题目本身：基础模式单独保留单格四方向的原始“一箭又一箭”判定，进阶模式再加入随机长箭、折光、反相、跃迁、棱镜、超载和连击。交互上坚持让玩家自己判断，悬停只做视觉高亮，不显示安全/危险答案；需要完整演示时可以主动启动 `A` 自动求解。正确点击后箭体会沿自身方向有序飞出窗口，而不是瞬间消失；同时保留低动态模式。程序每次启动都会先让玩家选模式与难度，并提供可直接双击的 Windows EXE。

如果之后继续做，我最想加的是每日固定种子和关卡编辑器，让不同的人可以挑战同一张图，而不只是各自在本地随机一局。
